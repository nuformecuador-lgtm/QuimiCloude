## Decisiones que el design no escribia (y por que)

1. **La plantilla se construye sobre un nombre intermedio y se renombra al final**
   (`qct_tplbuild_<huella>_<pid>` -> `ALTER DATABASE ... RENAME TO qct_tpl_<huella>`). El design no
   lo dice. Sin esto, una corrida matada a mitad de los ~40 s dejaria una plantilla **incompleta con
   el nombre bueno**, y R6 —«si existe, se reutiliza sin migrar»— la reutilizaria para siempre. Con
   el rename, el nombre bueno solo existe cuando la receta termino entera. Si la receta falla, la
   base intermedia se borra.
2. **Un 5.º paso: `prisma migrate status`.** `design.md > 3` dice que «lo que decide si la receta
   fue bien es el paso 4 seguido de `prisma migrate status`», pero no lo listaba como paso. Va
   dentro de `ensureTemplateDatabase` y se paga una vez por huella (~12 s de los 40).
3. **`PendingMigrations` es union discriminada** (`readable: true | false`), no un array que puede
   venir vacio: R16 exige distinguir «no falta ninguna» de «no se pudo comprobar», y con un array
   vacio las dos cosas se escriben igual.
4. **`dropRunDatabase` y `reclaimAbandonedDatabases` aceptan / resuelven la URL de desarrollo.** La
   firma del design es `(name) => Promise<void>` y `(worktreePath) => Promise<string[]>`; se respeta
   (el 2.º parametro es opcional). Cuando falta, `resolveDevelopmentUrl` la saca del entorno o del
   `.env`. Da igual que `DATABASE_URL` ya apunte a la base efimera en ese momento: de la URL solo se
   toman usuario/host/puerto y **todo el DDL va contra `postgres`**.
5. **La huella normaliza `\r\n` a `\n`** antes de hashear: un checkout de Windows y uno de Linux
   reconstruirian la plantilla sin que haya cambiado ninguna migracion.
6. **`spawnSync(..., { shell: true })`** para invocar `pnpm`: en Windows `pnpm` es un `.cmd` y
   `spawnSync` no lo resuelve solo. Los argumentos son constantes del archivo, no entra ningun dato
   de fuera.
7. **El directorio de rastros es `<worktreePath>/.qc-test-db/`.** El design no decia respecto a que
   ruta; anclarlo al worktree hace que R9 («rastros de ESTE worktree») sea cierto por construccion,
   y ademas se comprueba el campo `worktreePath` de cada rastro.

### 2. Crear y borrar 20 veces seguidas (R1, R7)

Cada vuelta comprueba ademas que el rastro **existe** tras crear y **no existe** tras borrar.

```
1:qct_qc77_7a512e99_mtykyy7qo_cfc ... 20:qct_qc77_7a512e99_mtykysnb_cfc
20 ciclos en 28251 ms
bases qct* al final: qct_tpl_1db8043a68e0

```

Los 20 nombres fueron distintos. **Al final no queda ninguna base de corrida ni ningun rastro**: lo
unico vivo con prefijo `qct_` es la plantilla, que es cache legitima. ~1,4 s por ciclo completo
(copia + `DROP`), frente a los ~40 s que costaria migrar y sembrar (alternativa A4).

### 3. La corrida que murio sin borrar su base (R9)

Se crea una base, se reescribe su rastro con un pid que no existe (999999) y se llama a
`reclaimAbandonedDatabases`:

```

```

**Control negativo, no pedido pero es la regla de oro de `wt.sh`:** un rastro con pid muerto pero
`worktreePath` de **otro** worktree **no se toca**:

```
reclamadas: (ninguna)
rastros: qct_ajena_deadbeef_1_1.json
```

### 4. Un nombre invalido se rechaza ANTES del DDL

```
rechazado antes del DDL: «QCT_MAYUS» -> test-db: «QCT_MAYUS» no es un nombre de base de test valido. Debe casar con /^qct_[a-z0-9_]{1,58}$/ ...
rechazado antes del DDL: «otra_base» -> ...
rechazado antes del DDL: «qct_aaaa...(60 a)» -> ...
rechazado antes del DDL: «qct_x"; DROP DATABASE y --» -> ...
```

Los cuatro lanzan sin abrir ninguna conexion. El ultimo es el caso que importa: un nombre con
comillas no llega nunca a un `CREATE`/`DROP DATABASE`.
