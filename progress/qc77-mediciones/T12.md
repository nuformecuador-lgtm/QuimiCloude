# check, se salta entero y el gate sigue verde. Que `scripts/test-db.ts` no exista es una rotura

# el detalle se fuera por stderr, el aviso prometeria una razon que no entrega.
SALIDA_DB=$(pnpm run db:test status 2>&1) || true
# Alternacion de literales, no `[✓!✗]`: una clase de caracteres con multibyte puede casar por
# byte suelto y cazar cualquier otro simbolo Unicode.

if [ -z "$VEREDICTO_DB" ]; then

    ok "$LINEA_DB"
  done
else

    warn "$LINEA_DB"

  case "$VEREDICTO_DB" in

  esac

### Decisiones del bloque

1. **`|| true` en la captura.** Con `set -euo pipefail`, si `db:test status` devolviera no-cero el
   gate se cortaria ahi. R15 dice que el estado de una base local **no** cambia el codigo de salida
   del gate, asi que no puede tumbar el init ni por accidente.
2. **`fail` si falta `scripts/test-db.ts`.** `docs/gate.md > El anti-patron: la validacion
   opcional`: un check colgado de `[ -f <script> ]` con un `warn` en el `else` no es un check. Que
   el script no exista es una rotura del arnes; que la base este atrasada es la circunstancia que
   el bloque vino a contar.
3. **`2>&1` en la captura.** El bloque **reimprime** lo capturado, asi que si el detalle se fuera
   por stderr el aviso prometeria una razon que no entrega (trampa conocida del mismo documento).
   Con `2>&1` el `! ...` o el `✗ ...` que el script escriba llega entero.
4. **`grep -E '^(✓|!|✗)'`, no `[✓!✗]`.** Una clase de caracteres con multibyte puede casar por byte
   suelto; la alternacion de literales no.
5. **Se reemite con el `warn`/`ok` del propio gate.** `scripts/test-db.ts` solo colorea si hay TTY;
   reemitir garantiza el amarillo del gate tambien cuando la salida se redirige a archivo — que es
   justo como se leen los codigos de salida aqui abajo.
6. **La coletilla «los tests de integracion no se ven afectados» solo si la base VA ATRAS.** Cuando
   no se pudo consultar, afirmar que «la app a mano si se ve afectada» seria decir algo que el gate
   no sabe (R16 exige distinguir los dos desenlaces, no confundirlos).
